# MCPay / Frames на Stellar: стоит ли делать для HackMeridian

> Ранняя оценка, сохранённая для контекста. Последующее исследование нашло MPP Router и AgentSmith: поставку платных API и значительную часть инфраструктуры можно взять готовыми. Актуальный план — в [HackMeridian research](hackmeridian-research.md).

Проверено 25 октября 2026 года. Оценка основана на публичном коде, документации и ответах API. Чужие платные вызовы и рыночный спрос экспериментально не проверялись.

## Рекомендация

Перенос «MCPay, только на Stellar» — слабая самостоятельная идея. Платёжная инфраструктура и поиск оплачиваемых MCP/HTTP-инструментов на Stellar уже представлены несколькими публичными проектами. Осмысленный хакатонный проект здесь — конкретное приложение, которое использует готовые платежи и решает задачу реального покупателя. Разработка ещё одного общего каталога, facilitator или F1-подобного роутера за оставшееся время будет конкурировать с уже существующими компонентами и отвлечёт от демонстрации пользы.

Наличие конкурентов подтверждает интерес разработчиков к направлению, но не доказывает платёжеспособный спрос. Для продолжения после хакатона нужны повторные покупки полезных услуг независимыми пользователями.

## MCPay действительно связан с Frames

Домен [mcpay.tech](https://mcpay.tech/) перенаправляет на Frames. Владелец [репозитория MCPay](https://github.com/microchipgnu/MCPay), Luís Freitas, указан среди авторов [анонса Frames F1](https://frames.ag/blog/introducing-frames-f1). Это сильное подтверждение продуктовой преемственности. Буквальное переименование репозитория или перенос конкретного серверного кода не установлены.

MCPay предлагает реестр сервисов, обёртку для монетизации MCP/HTTP, клиентский SDK/CLI и согласование оплаты через x402. Frames расширяет предложение: поиск и выбор поставщика данных, проверка доставки, учёт расходов и управляемый F1. Это существенно больше, чем добавление нового платёжного метода. [MCPay README](https://github.com/microchipgnu/MCPay), [Frames HTTP tools](https://frames.ag/docs/tool-endpoints).

## Что показал разбор Frames через REA

Использован REA 6.8.0 через CLI. Сохранены 52 публичных JS-файла общим размером 3 001 696 байт. Для целевого статического анализа выбраны пять файлов, связанных с auth, API, каталогом и запуском задач. Они разобраны без синтаксических ошибок. Семантический граф частичный: достигнуты лимиты удержания узлов; остальные 47 файлов не анализировались REA. Это не восстановление серверного исходного кода.

Ручная проверка клиентских файлов и публичных ответов API дополнила REA:

- `/catalog-api/_meta` перечисляет источники обновления: Bazaar, probe-discovery, Agentic Market, paysh, MPP Directory, mppscan, x402scan, frames-registry и submitted. Наличие записи в этом ответе не доказывает качество соответствующего импорта.
- `/catalog-api/catalog?quality=any&limit=1` вернул `total: 39237`. Это заявленный сервером размер каталога, а не 39 тысяч проверенных работающих интеграций.
- Поиск `company funding` вернул `x-search: hybrid:30`; внутренние модели и формула ранжирования не установлены.
- Каталог содержит не только прямых поставщиков: среди найденных результатов есть посредник Orthogonal. Количество tools нельзя приравнивать к количеству независимых источников данных.
- В клиенте видны Better Auth, `api.frames.ag`, проектные API-ключи, SSE с Last-Event-ID и polling долгих run.
- Публичный `/v1/tools/spec` описывает direct invoke, а не только F1. В нём цена доставленного вызова указана как `seller_price × 1.15 + $0.005`; pending/async и некоторые непроверяемые оплаченные результаты имеют отдельное правило. Поэтому обещание «нет полезного результата — никаких списаний» нельзя механически воспроизвести без точного контракта возвратов.

Вывод для продукта: сложность Frames находится в качестве каталога, выборе источника, исполнении, проверке результата и учёте денег. Перенос settlement на Stellar сам по себе эти задачи не решает. [Публичный spec](https://api.frames.ag/v1/tools/spec), [каталог](https://frames.ag/index).

## Где Stellar даёт содержательную пользу

Stellar подходит для расчётов в USDC за отдельные вызовы и для программируемой авторизации расходов. Пользователь может делегировать агенту ограниченные права, сохранив контроль через правила smart account. Из этого можно собрать понятный продукт: бюджет на конкретную задачу, ограниченный срок доступа, разрешённые получатели и журнал покупок.

Однако spending cap сам по себе уже есть у других проектов. Отличие должно быть в законченном рабочем процессе и удобстве внедрения. Совместимость выбранного smart account signer с конкретным x402 client/facilitator нужно проверить реальным платёжным циклом до обещания этой функции в демо. [Stellar x402](https://developers.stellar.org/docs/build/agentic-payments/x402), [OZ authorization](https://docs.openzeppelin.com/stellar-contracts/accounts/smart-account).

Stellar не даёт автоматического доступа к чужим услугам на Base/Solana/Tempo. Поставщик должен принимать Stellar либо наш сервис должен отдельно оплачивать его на поддерживаемой сети. Второй вариант добавляет финансирование кошельков, обмен, ошибки и учёт; для первого MVP его лучше исключить.

Контракт также не может сам определить качество произвольного текста, отчёта или лида. Он может проверить подпись, лимит, срок и получателя. Гарантия полезного результата требует отдельно определённой проверки, доверенного арбитра или соглашения с продавцом.

## Какой MVP имеет смысл

Предлагаемая гипотеза: приложение для одной повторяющейся задачи, где агент покупает услуги двух независимых провайдеров в рамках выданного бюджета и возвращает полезный результат вместе с расходами и квитанциями. Нишу следует выбрать по доступному пользователю и данным, а не по красоте инфраструктуры. Возможный пример — платные проверки Soroban-контракта перед публикацией, если есть команда-покупатель и поставщик действительно полезной проверки. Это пример для проверки спроса, не установленная свободная ниша.

Минимальное демо:

1. Человек выдаёт задачу и небольшой бюджет в testnet USDC.
2. Агент находит и покупает две реальные услуги по заранее раскрытым ценам.
3. Поставщики получают Stellar-платежи; интерфейс показывает результат и ссылки на транзакции.
4. Повтор с тем же idempotency key не создаёт вторую покупку.
5. Попытка превысить бюджет блокируется. Если заявлен onchain limit, отказ должен происходить в авторизации контракта, а не только в интерфейсе.

Полезнее подключить внешнюю команду или существующий сервис, чем наполнить каталог собственными фиктивными погодными API. Платежи за бесплатную публичную информацию без добавленной ценности не подтверждают продуктовую гипотезу.

Практический критерий решения: за первые два часа найти одного конкретного покупателя, полезный платный endpoint и пройти один сквозной платёж. Если этого нет, сменить сценарий. Расширять каталог до подтверждения этого цикла не стоит.

## Соответствие HackMeridian

Для новой идеи подходит Genesis / Stellar Composed: организаторы прямо приводят пример агентов, которые используют кошельки, OpenZeppelin policies и x402/MPP. Соответствие теме оценивается в 20%, пользовательская проблема — в 20%, техническое исполнение — в 15%, инновация — в 15%. Само попадание в тему не компенсирует отсутствие полезного сценария. [Правила и критерии](https://www.hackmeridian.com/build).

Подача закрывается **26 октября 2026 в 12:00 по Лиссабону**. Жюри смотрит видео, pitch deck, репозиторий и ответы в заявке. Для оставшегося времени разумнее один законченный workflow с реальными транзакциями и честными ограничениями, чем широкая копия Frames. [Расписание](https://www.hackmeridian.com/schedule).

Моя оценка: копия MCPay с заменой сети — слабый выбор; конкретное приложение поверх готовых Stellar rails — разумная хакатонная ставка при наличии пользователя и полезного поставщика. Оснований обещать выигрыш или коммерческий успех пока нет.

## Дополнительная живая проверка Rail402

25 октября 2026 года endpoint `/supported` ответил и объявил `stellar:testnet`, схемы `exact`/`upto` и расширение Bazaar. `/discovery/resources?limit=5` вернул `pagination.total: 9`; в пяти полученных записях все URL принадлежали `demo.rail402.dev`, включая HTTP и MCP. Поиск `search` вернул пустой список. Это подтверждает доступность discovery API, но не проведение нами платежа и не наличие большого независимого каталога. [Supported](https://testnet.rail402.dev/supported), [каталог](https://testnet.rail402.dev/discovery/resources?limit=5).

README MCP-пакета перечисляет `search_stellar_resources`, `pay_and_call` и `get_budget`; это близко к обсуждаемому единому MCP для поиска и оплаты инструментов. Клиентский бюджет описан как локальный SQLite ledger, его нельзя автоматически считать onchain ограничением. [MCP-пакет](https://github.com/tolgayayci/rail402/tree/main/packages/mcp).

Поэтому следует различать существование нужной архитектуры на Stellar и наличие развитого продукта с широким набором полезных поставщиков: первое подтверждено опубликованной реализацией; второе этой проверкой не установлено.
